# 分析框架使用场景与结果应用

> **创建日期**：2026-06-01
> **配套文件**：《服务设计分析框架（修正版）V2.0》

---

## 一、使用场景

框架不是"每天用的东西"，它在5种具体场景下被调用。其他时间归零到日常运营——只执行已设计好的触点标准。

### 场景A：设计新体验

**触发条件**：决定推出一个新付费产品/活动时。

**示例**：推出一堂"夏夜松林篝火故事会"（引擎B+核心层联动）。

| 调用层 | 产出 | 耗时参考 |
|:---|:---|:---:|
| ①画像 | 确定面向"亲子教育型+深度归属型"两类 | 15分钟 |
| ②场景 | 夏夜周末、家庭结伴、计划型消费、预计停留2-3小时 | 10分钟 |
| ③生产约束 | 篝火台是否已建好、夏季防火条件是否允许 | 5分钟 |
| ④体验任务 | 功能：有篝火+故事+亲手烤棉花糖；情绪：夏夜的仪式感+孩子兴奋+家长放松 | 20分钟 |
| ⑤⇄⑥情绪曲线+触点 | 交替迭代2轮，输出触点设计 | 40分钟 |
| ⑦能力匹配 | 现有场地/人员/道具能否支持 | 15分钟 |
| ⑧输出 | 体验旅程文档+触点执行标准 | 20分钟 |
| **合计** | | **约2小时** |

**频次**：按农事节奏，每月0.5-2次。

### 场景B：优化现有体验

**触发条件**：某个成熟活动的客户反馈下降/复购率下滑/被投诉。

**示例**：自然教育引流课（68元）课后满意度从4.2降到3.5。

| 调用层 | 产出 | 耗时参考 |
|:---|:---|:---:|
| ⑤情绪曲线 | 画出当前课程的实际情绪曲线（对比设计预期） | 15分钟 |
| ⑥触点 | 逐一检查P0触点是否达标 | 20分钟 |
| ④体验任务 | 重新确认四层任务是否全部满足 | 10分钟 |
| ⑦能力匹配 | 识别差距（是流程问题/人问题/还是课程内容本身问题） | 10分钟 |
| **合计** | | **约1小时** |

**频次**：按需，估计每月0-2次。

### 场景C：季度战略校准

**触发条件**：每季度末，言渊+各板块主理人一起做。

**内容**：

| 调用层 | 产出 | 耗时参考 |
|:---|:---|:---|
| ①画像校准 | 更新各画像的实际到店比例和客单价数据 | 30分钟 |
| ⑨数据反馈 | 框架预测vs实际情况的匹配率分析 | 20分钟 |
| ②场景修正 | 是否有新的触发场景出现？原有场景判断是否需要调整？ | 15分钟 |
| ④体验任务 | 客户的四层任务是否有变化？ | 15分钟 |
| **合计** | | **约1.5小时** |

**频次**：每季度固定1次。

### 场景D：半年归零复盘

**触发条件**：每6个月一次，全团队参加。

**内容**：全9层逐层复盘，核心问题列表见框架第⑨层。

**耗时**：3-4小时。

**频次**：每6个月1次。

### 场景E：日常运营巡检

**触发条件**：每天早上/每次活动前。

**调用层**：仅第⑥层P0触点（到达/体验/服务/离开）。

**内容**：今天P0触点准备好了没有？洗手间干净吗？核心体验物资齐了吗？今天负责服务的人是谁？

**耗时**：5-10分钟。

**频次**：每天。

## 二、分析结果如何用

框架跑完不是终点——跑出"方案"只是中间产物。分析结果必须落到三个地方才算真正使用。

### 落点一：触点执行标准

每个活动/产品跑完框架后，输出一张**触点执行卡片**——这是给一线执行的人看的，不是给言渊看的。

**模板**：

```
活动名称：______
负责主理人：______
日期：______

P0触点执行标准：
□ 到达——停车场到入口有指引，洗手间已检查，主理人在入口等候
□ 体验——核心流程已走一遍，所有物资备齐，备用方案（雨天/高温）已确认
□ 服务——今天谁负责接待，谁负责核心交付，谁负责收尾
□ 离开——拍照设备已准备，可带走的成品已备好

P1触点执行标准：
□ 决策——价格/内容/时间信息已发布
□ 后续——客户信息记录表已打印

异常预案：
□ 客户超出预期人数 → 备用物资在哪里
□ 核心主理人临时不在 → 替代人是谁
□ 天气突变 → 室内备用场地在哪
```

**使用方式**：每场活动前由执行人逐项打钩确认。不打钩不开场。

**存放位置**：打印张贴在各活动区域（面包窑旁/教室墙上/露营登记处）。

### 落点二：资源配置决策

框架的输出直接回答农场经营中的两个核心资源问题：

| 问题 | 由框架哪层回答 | 决策示例 |
|:---|:---|:---|
| **钱花在哪** | ①画像优先级 + ②场景频次 | "银发活力型置信度只有★☆☆☆☆，不单独投入。亲子教育型置信度高、升级路径清晰，8月重点推探索营" |
| **人放在哪** | ⑥触点P0/P1 + ⑧能力匹配 | "到达触点人手不够→安排兼职负责周末引导。体验触点质量下降→种植养殖主管本周不安排其他任务，专心打磨课程" |

**使用方式**：季度战略校准结束后，言渊根据框架分析结果调整下一季度资源配置优先级。调整结果写入月度工作计划。

### 落点三：产品迭代依据

当一个活动的复购率下降或满意度下滑时，不是拍脑袋改内容，而是回到框架中找出具体哪一层出了问题：

| 问题信号 | 可能出问题的层 | 排查方向 |
|:---|:---|:---|
| 客户来了但不满意 | ⑤情绪曲线 | 实际体验节奏与客户预期不符 |
| 客户来了一次不再来 | ④体验任务 | 缺少某层任务（常见为缺社交任务——没东西可发朋友圈） |
| 客户抱怨"和宣传的不一样" | ②场景 | 内容传递的预期与实际体验不匹配 |
| 客户觉得"不值这个价" | ⑥触点-离开 | 没带走够多的价值感 |
| 客户觉得"服务冷淡" | ⑥触点-服务 | P0服务触点执行不到位 |
| 特定画像的客户始终不来 | ①画像 | 画像假设有误——这类人并不存在 |

**使用方式**：出现问题→对照上表找到对应的框架层→用该层的分析工具重新跑→输出调整方案。

## 三、不使用框架的三种情况

框架有明确的适用范围。以下情况不需要使用：

1. **日常重复性执行**。已经跑通过的活动，按触点执行卡片操作即可，不需要重新分析。只在出现质量下降时用场景B回溯。

2. **纯运营管理决策**。排班、采购、招聘、财务——这些不需要服务设计框架。

3. **客户临时提出的微小需求**。比如说"能不能多给我一个袋子"、"能不能换个口味"——直接回答即可，不需要回框架分析。

**判断标准**：凡是涉及"要不要做一个新的体验产品"或"现有的体验为什么变差了"这两个问题，用框架。其他时候不用。

---

## 四、一句话总结

框架的使用场景是**五个**：设新计（A）、优化旧（B）、季度校（C）、半年复盘（D）、每日巡检（E）。

分析结果的落地是**三个**：触点执行卡片（每场活动前打钩）、资源配置决策（季度会后调整）、产品迭代排查（出问题时溯源）。

框架不用来判断"今天喂不喂鸡"——它用来判断"喂鸡这件事，怎么让客户参与、客户体验怎么样、下次怎么改进"。
